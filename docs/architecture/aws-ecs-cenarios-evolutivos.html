Formação AWS · Projeto BIA

Uma aplicação, três infraestruturas

A BIA é a mesma imagem de container do início ao fim. O que muda, cenário a cenário, é quanto de ECS o aluno precisa operar: primeiro sem balanceador, depois com ALB, depois com cache como serviço próprio em awsvpc. Este documento registra a arquitetura de cada estágio exatamente como definido em .kiro/rules/infraestrutura.md — e onde uma regra não especifica algo, isso é sinalizado em vez de inventado. Antes dos três cenários, a seção abaixo mostra onde tudo está de fato rodando hoje: o sandbox bia-dev, sem ECS nenhum ainda.

Antes do ECS

Estado atual — sandbox bia-dev no ar

Nenhum dos três cenários abaixo existe na AWS ainda. O que existe hoje é uma única EC2 (bia-dev) rodando quatro containers Docker lado a lado — a aplicação, uma segunda cópia de teste, o Postgres e o Redis — tudo na mesma máquina, sem ECS, sem ALB, sem separação de rede entre eles além do que o próprio Docker isola. É o ambiente de estudo; os cenários 1–3 são a rota de evolução, não o que está publicado.

Duas coisas que ainda não travam

O IP público (54.83.241.43) pode mudar se a instância for desligada e religada — não há Elastic IP configurado. E o SG real desta instância se chama bia-dev-sg, enquanto a rule de infraestrutura descreve o nome-alvo como bia-dev; vale alinhar o nome quando este sandbox for reorganizado, mas não é um erro que impeça o funcionamento hoje.

Por que os cenários abaixo existem

O diagrama anterior do projeto (docs/architecture/aws-ecs-diagram.html) desenha NAT Gateway, subnets privadas, RDS Multi-AZ e Secrets Manager — tudo isso a rule de infraestrutura pede explicitamente para não incluir, porque o público é aluno em etapa inicial e a prioridade é simplicidade sobre robustez de produção. Os três cenários a seguir são a rota de evolução real, a partir do sandbox bia-dev acima — nenhum deles está publicado na AWS ainda.

1Sem ALB — o essencial do ECS

Uma instância t3.micro roda o cluster ECS, uma task e um serviço. Sem balanceador, sem múltiplas zonas — o objetivo aqui é só o aluno ver o container vivo dentro de um cluster ECS/EC2, e o serviço falando com o RDS existente.

2Com ALB — alta disponibilidade mínima

Entra o Application Load Balancer, esticado entre zona A e zona B, cada uma com sua própria instância ECS/EC2. O ganho didático: o aluno passa a lidar com target group, portas dinâmicas do ECS e um security group que só existe para representar "vindo do ALB" — sem precisar de Multi-AZ no banco para isso.

Estágio 3 de 3

3Com ALB + Cache — awsvpc e service discovery

Salto conceitual: cada task ganha ENI própria (awsvpc), então o security group sai da EC2 e vai para a task. A EC2 (bia-cluster) fica com inbound vazio — quem decide quem fala com quem agora são bia-app e bia-cache. O cache aparece como um segundo serviço ECS, resolvido via Cloud Map, sem IP fixo hardcoded.

Comum aos três cenários

Pipeline: do git push ao rolling update

Independente do cenário, o deploy é o mesmo buildspec.yml: CodePipeline dispara no push ao GitHub, CodeBuild builda e publica no ECR, e o imagedefinitions.json gerado no final vira o gatilho do deploy no serviço ECS correspondente.

Fontes: .kiro/rules/infraestrutura.md, .kiro/rules/pipeline.md, buildspec.yml. Onde uma regra não especifica um comportamento (ex.: inbound de bia-web no Cenário 1), este documento sinaliza a lacuna em vez de presumir um valor.
